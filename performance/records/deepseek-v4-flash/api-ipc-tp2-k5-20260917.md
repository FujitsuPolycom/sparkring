# DeepSeek TP2 API and IPC observations

Status: **research-only**. Two bounded experiments completed with five-token
DSpark speculation. The observations support further testing of the optional
IPC setting; they do not promote a default or establish performance, power or
long-term reliability improvements.

## Runtime

Two GB10 systems served the locally available DeepSeek-V4-Flash-0731 model with
TP2/DCP1, 16 GiB `fp8_ds_mla` KV per rank, 1M configured context, 32 sequences
and a 4096-token batch budget. External caching was disabled. Both experiments
used the same per-rank image pair, built from source
`9f5b1e619d037d1ae365f158135c3de42402cf4e`:

| Rank | Local image ID |
|---|---|
| 0 | `sha256:d461d8c1f6465f3f21b2af40e0e56763282f016776bc7d72436ad13675a03a87` |
| 1 | `sha256:26f201e09a77e8e1d0b27bc0ee7f2479a46836eb7b71a7ea7b2c253aaf4d2f1d` |

The independent builds preserved the compiled native library from parent image
`41fc632d0235…` / published manifest `827a8e8c…`; its SHA256 remained
`58c4c2e7acdbbacc58d41f1326f63e10b8bc9d0dbf406a2dea22234d7f64dad2`.
The [JSON record](api-ipc-tp2-k5-20260917.json) contains full identities, build
context, model metadata/presence scope, source hashes and unrounded measurements.
Weight payload checksums and revision provenance were not reverified.

The IPC constructor source hash was
`8cbdb643a7dce4dc291fcfbdf690c6d9ee22ef1b7520aa65e905981ee08f22c2`.
Its build preflight imported the actual installed module and constructed real
ZeroMQ readers/writers for the default, 2 ms, zero and 1 s settings. This includes
the dependency correction for the earlier missing-`os` startup failure; that
failed image is excluded from these results.

## API results

On the 1 s arm, all eight named/required tool checks passed: four positive calls,
two full-response HTTP 500 `ToolChoiceContractError` results, and two HTTP 200
streams carrying that explicit SSE error and `[DONE]`. The unmodified parent
had already returned HTTP 500 `InternalServerError` for its full one-token
requests; its streaming requests reproduced HTTP 200 with empty calls. The
combined API upgrade and wrapper were not isolated from each other, so every
error result cannot be attributed solely to the wrapper. The eight-case matrix
was not repeated on the 2 ms arm.

Both arms completed Responses requests with `reasoning.effort: "max"`, in full
and streaming modes. Streaming `response.created`, `response.in_progress` and
`response.completed` events retained `max`. These are bounded contract checks,
not general API-conformance or model-quality qualification.

## IPC measurements

Only `SPARKRING_SHM_BUSY_LOOP_S` changed between the two serving arms. Three
batches at each concurrency used 1024 prompt tokens and 128 generated tokens per
request. Rates include prompt processing and queueing: total completion tokens
divided by concurrent batch wall time.

| Concurrent requests | Median aggregate end-to-end tok/s, 1 s | 2 ms |
|---:|---:|---:|
| 1 | 55.82 | 55.21 |
| 4 | 108.56 | 110.47 |
| 8 | 138.98 | 138.67 |

CPU percentages sum user and system CPU time for container processes present
in both `/proc` samples. **100% equals one occupied logical CPU**, rather than
the entire host. The JSON retains each measured PID, process name, interval and
percentage. Raw cumulative tick snapshots were not retained.

| Host role | Workload CPU, 1 s | Workload CPU, 2 ms | Observation intervals |
|---|---:|---:|---|
| Rank 0 | 291.33% | 142.47% | 50.52 s / 51.82 s |
| Rank 1 | 134.37% | 137.41% | 50.79 s / 51.82 s |

Rank-zero CPU use was lower in this short observation; rank-one CPU use was
similar. This does not establish causality, significance, power savings or a
default recommendation. The 1 s control received 36 calibration requests
before benchmarking; the 2 ms arm did not. Warmup/cache histories therefore
differ. The prompt-processing singletons are retained as observations and
cannot establish a prefill improvement or regression.

## Remaining checks

[Issue #189](https://github.com/FujitsuPolycom/sparkring/issues/189) still needs
matched warmup, cancellation, idle/burst latency tails, complete-queue
notification reliability, restart coverage and a longer stability run before
default promotion. Three batches and one CPU interval per arm do not supply
those guarantees.

The 1 s control also recorded nine post-readiness preparation-kernel warning
events per rank, including `last_sampled_ptr=*i64`. These are not nine proven
distinct cache keys. Typed specialization work remains separate;
[issue #188](https://github.com/FujitsuPolycom/sparkring/issues/188) is not
resolved by these results. The monitor can report disk loading as well as
compilation, so these events do not establish cold compile cost or complete
warmup coverage. Published images and profile defaults remain unchanged.
