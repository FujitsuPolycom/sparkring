# MiMo-V2.6-Flash-RL on two and four Sparks with the installer image

Status: **implemented; installations of both profiles through `install.sh`
measured on one pair and one four-Spark ring; single-run timing; not
serving-qualified**.

The four-Spark profile `mimo-v26-flash-rl-tp4` sets
`NCCL_IB_EXTENDED_IPV4_GIDS=1`. Each Spark exposes its two ring ports as four
NIC functions across two PCIe domains, and the image's NCCL 2.32.3 publishes
all four only with this setting. On one ring, with every other setting equal,
prefill of 8K to 128K-token prompts was 11-17% faster with it on, and decode
verification steps per second at 1, 8 and 16 streams were unchanged. The
two-Spark profile pins two NIC functions and does not set it.

## Conditions

- **Four Sparks, extended GIDs off:** `install.sh --profile
  mimo-v26-flash-rl-tp4 --yes --json` from commit `418c98775250`, whose MiMo
  four-Spark profile had the setting off, installed the profile on image
  `dev-20260927-b12xcache-cuda1342-nccl2323-status032`, adopting the
  checkpoint copies already on the Sparks. The API was ready 394 s after the
  model started. The benchmark ran twice on this deployment.
- **Four Sparks, extended GIDs on:** serving containers derived from that
  installation's Compose files with only `NCCL_IB_EXTENDED_IPV4_GIDS=1` added
  ([`envab.py`](dev-20260927-b12xcache-mimo-v26-20260927/programs/envab.py)),
  healthy 200 s after launch; then `install.sh` from commit `e9d998406c92`,
  whose profile sets it, on the same image. That installation's API was
  ready 213 s after the model started, with every B12X kernel selection taken
  from the cache and no compilation. All four-Spark runs used the same Sparks
  and checkpoint copies.
- **Two Sparks:** the published one-line command at commit `c17cf23cec72`
  installed `mimo-v26-flash-rl-tp2` on one directly cabled pair, on image
  `dev-20260927-h2dstaging-cuda1342-nccl2323-status031`; the API was ready
  550 s after the model started. That commit's pair profile settings equal
  those of the commit that adds this record except the image, which adds a
  B12X selection-cache correction applied at startup and runtime-status
  0.3.2 to the measured image.
- **Client:** a separate machine on Node A's network.

## Measurement

[llm-inference-bench](https://github.com/local-inference-lab/llm-inference-bench)
`llm_decode_bench.py` 0.6.2 at temperature 1.0 with exact token targeting,
1, 8 and 16 concurrent streams, no added context, 20 s per cell after a 5 s
warm-up, up to 2,048 output tokens with end of sequence ignored. Decode is the
aggregate output rate from stream usage. Prefill is a cold scout-only prompt's
length divided by its time to first token. Steps per second and tokens per
step come from vLLM's speculative-decoding counters. Each run measures each cell once.

## Conclusion

Extended IPv4 GIDs raise four-Spark prefill by 17%, 13% and 11% at 8K, 64K
and 128K tokens and leave the decode step rate unchanged, so the four-Spark
profile sets them. Prefill repeated within 0.5% for each setting. Decode
throughput varies between runs with the tokens accepted per step, which
follow the sampled text at temperature 1.0: two runs of the same deployment
differed by 16% at one stream at equal step rates.

## Limits

The four-Spark configurations ran on one ring and the pair profile on one
pair; the pair profile's benchmark ran once. Prefill is one cold prompt per
length and run.
