# Qwen3.8 Flash Next decode A/B on the installer image

Status: **implemented; single-run A/B at concurrency 1; not serving-qualified**.

This record compares Qwen3.8 Flash Next NVFP4 checkpoints and draft lengths
for single-stream decode on image `dev-20260925-cuda1342-nccl2323-status031`
(configuration
`sha256:5ce6ce267d8069215e08da87be3a8092175e63806cf97730847405eb04a2c51f`),
on one directly cabled Spark pair (TP2) and one four-Spark ring (TP4). The
[machine-readable record](decode-ab-20260925.json) holds every measured value.

## Conditions

Each variant ran in serving containers derived from the installer
deployment's per-rank Compose files by
[`qwab.py`](decode-ab-20260925/qwab.py). A variant changes only the settings
that [`variants.json`](decode-ab-20260925/variants.json) lists. Everything
else stays as the installer deployment sets it: image, transport, memory, HC
token-row prefill ownership and prefill features. A variant with another
checkpoint also moves every cache path to that checkpoint's revision.

| Variant | Checkpoint | Draft MoE backend | Draft tokens |
|---|---|---|---|
| `ple-s3` | `60215d26cf5e` (branch `qad-step5500-ple1000`): BF16 attention, MXFP8 MTP experts | humming | 3 |
| `main-s3` | `629bc3218833`: MXFP8 attention, NVFP4 MTP experts | B12X | 3 |
| `main-s2` | `629bc3218833` | B12X | 2 |
| `main-s4` | `629bc3218833` | B12X | 4 |
| `main-s3-mxfp8head` | `629bc3218833`, MXFP8 target LM head | B12X | 3 |
| `main-s3-skinny` | `629bc3218833`, SM121 skinny-GEMM overlay | B12X | 3 |
| `mxhead-adaptive` | `629bc3218833`, MXFP8 target LM head | B12X | adaptive, at most 3 |

[`measure.sh`](decode-ab-20260925/measure.sh) runs a discarded warm-up pass,
then:
- **checks:** counting, 17×23 and `is_prime` requests;
- **decode by prompt type:** [`decode_probe.py`](decode-ab-20260925/decode_probe.py)
  runs two 512-token greedy runs each for a story (prose), a Python module
  (code) and a JSON array (JSON). It reports end-to-end tokens/s and draft
  acceptance from the server's speculative-decoding counters;
- **prefill:** time to first token at about 4K, 16K and 64K prompt tokens.

## Results

Decode in end-to-end tokens/s, prefill in tokens/s. Every variant passed the
checks.

| Cluster | Variant | Prose | Code | JSON | Prefill 4K / 16K / 64K |
|---|---|---|---|---|---|
| TP2 | `ple-s3` | 47.9 | 73.2 | 81.0 | 4040 / 4186 / 3822 |
| TP2 | `main-s3` | 53.8 | 82.0 | 92.2 | 3417 / 4255 / 3920 |
| TP4 | `ple-s3` | 68.2 | 104.6 | 113.3 | 4587 / 4474 / 4177 |
| TP4 | `main-s3` | 73.8 | 116.9 | 125.5 | 4379 / 4532 / 4239 |
| TP4 | `main-s2` | 75.9 | 101.1 | 108.6 | 4410 / 4507 / 4200 |
| TP4 | `main-s4` | 62.2 | 99.3 | 117.5 | 4338 / 4488 / 4188 |

Revision `629bc3218833` with three B12X draft tokens decoded 12–14% faster
than the `qad-step5500-ple1000` export on TP2 and 8–12% faster on TP4. Draft
acceptance was similar, so the gain comes from shorter decode steps: MXFP8
attention reads half the bytes of BF16 attention, and the NVFP4 draft experts
run on B12X. Prefill stayed within 3%, except one TP2 4K run whose first
repetition measured 0.98 s (4,148 tokens/s). Two draft tokens gained 3% on
prose and lost 13% on code and JSON. Four draft tokens lost on every prompt
type, because each extra draft pass adds latency.

Installer deployments of `main-s3`, run after the installer profiles pinned
that revision, reproduced the variant: TP2 54.2 / 81.5 / 93.2 and TP4 76.0 /
112.5 / 125.2 tokens/s for prose / code / JSON. Prefill was 4004 / 4252 /
3897 and 4319 / 4503 / 4206 tokens/s.

## MXFP8 target LM head

Variant `main-s3-mxfp8head` sets `VLLM_MXFP8_LM_HEAD=1`. The server then
quantizes the target (verifier) LM head from BF16 to MXFP8 at load; the MTP
draft keeps its NVFP4 head.

| Cluster | Prose | Code | JSON | Prefill 4K / 16K / 64K |
|---|---|---|---|---|
| TP2 | 60.6 | 86.9 | 96.4 | 4009 / 4277 / 3940 |
| TP4 | 80.1 | 117.1 | 127.6 | 4637 / 4513 / 4231 |

Per-step time fell by about 3%, because the head's 248,320 × 2,560 weights
are read at half the bytes. After the installer profiles adopted the setting,
installer deployments measured TP2 56.4 / 85.4 / 95.1 and TP4 80.7 / 115.0 /
125.5 tokens/s for prose / code / JSON. That is 2–5% above the BF16-head
installer deployments, except TP4 JSON at 0.3%. Prefill stayed within 3%.

Prose rates move with draft acceptance. Restarts of one configuration
generate slightly different greedy text, and position-1 prose acceptance
ranged from 0.63 to 0.72 across these runs. The derived-container
measurements above (60.6 and 80.1 tokens/s for prose) include such a swing.
Per-step time, the after-first-token rate divided by tokens per step, is the
more stable comparison.

[`logprob_probe.py`](decode-ab-20260925/logprob_probe.py) scored one fixed
1,151-token text (prose, Python and JSON) with `prompt_logprobs` on each
configuration:

| Comparison | Mean \|Δ log-prob\| | 99th percentile | Rank-1 agreement |
|---|---|---|---|
| TP2, MXFP8 head vs BF16 head | 0.033 | 0.62 | 98.5% |
| TP4, MXFP8 head vs BF16 head | 0.037 | 0.77 | 97.8% |
| BF16 head, TP2 vs TP4 | 0.035 | 0.61 | 97.9% |

Quantizing the head changed token log-probabilities about as much as running
the BF16 head on two ranks instead of four. One text does not establish task
accuracy.

## SM121 skinny-GEMM plans

[`bench_skinny.py`](decode-ab-20260925/bench_skinny.py) measured vLLM's CuTe
skinny GEMM against torch linear for the model's BF16 projection shapes on
one GB10, replaying CUDA graphs with weights read from memory. The results
are in [`gb10-skinny-gemm-sweep.json`](decode-ab-20260925/gb10-skinny-gemm-sweep.json).
Correct configurations were 8–14% faster for the hyper-connection
projections, up to 29% for the router, and 1.4–1.6× for single-row draft
projections. For the four-row verification batch, the LM head gained 5–6%.

Variant `main-s3-skinny` mounts an overlay built by
[`skinny_overlay.py`](decode-ab-20260925/skinny_overlay.py). The overlay adds
the measured SM121 plan table, calls the low-latency hook with B12X active,
and re-seals the receipts. Every per-layer BF16 projection and most draft
projections selected a plan. Decode steps shortened by about 1% on TP2 and
3% on TP4: TP2 55.2 / 84.1 / 92.7 and TP4 76.7 / 117.0 / 128.2 tokens/s
for prose / code / JSON. Prefill was unchanged. The overlay is an experiment
container change, not part of the serving image.

## Adaptive draft length

Variant `mxhead-adaptive` adds `adaptive_speculative_tokens_window: 32` and
`adaptive_speculative_tokens_initial: 3` to the MXFP8-head configuration.
vLLM then adapts the draft length from recent accepted lengths, with three
as the upper bound. Prose drafted two tokens per step, and code drafted three
tokens in most steps. Against the installer deployments, prose changed by
+1.7% on TP2 and −6.8% on TP4, code by −2.6% and +2.0%, and JSON by +0.8%
and +2.9%. These differences are within the restart-to-restart acceptance
variation, so the profiles keep a fixed three-token draft.

## Decode step profile

A torch profiler trace of one 64-token prose request on TP2 `main-s3` is
summarized in [`tp2-main-s3-profile-summary.txt`](decode-ab-20260925/tp2-main-s3-profile-summary.txt),
produced by [`trace_breakdown.py`](decode-ab-20260925/trace_breakdown.py).
The GPU was busy for 98% of the traced window, and collectives took 4% of
kernel time. Dense GEMMs took 57% and routed-expert MoE kernels 26%.

About 29 MB of BF16 weights per layer are replicated on every rank: the
hyper-connection mixing projections and the router, which together take about
0.17 ms per layer on TP2. The image's Qwen4Exp skinny-GEMM decode plans cover
H200 and B300 only, so these projections use the standard linear
implementation on the Spark.

## Limits

Each variant ran once at concurrency 1 with short contexts. The derived
containers share the installer deployment's settings but are not installer
deployments. Acceptance and throughput depend on prompt content, so the three
prompt types bound rather than define a workload's rate.
