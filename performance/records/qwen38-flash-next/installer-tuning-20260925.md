# Qwen3.8 Flash Next installer tuning: decode image, collectives and TP4 prefill

Status: **implemented; measured in serving containers derived from installer
deployments on one TP2 pair and one TP4 ring; not serving-qualified**.

This record gives the measurements behind the Qwen installer profiles'
decode and prefill settings on image
`dev-20260925-qwendecode-cuda1342-nccl2323-status031` (configuration
`sha256:4100e1d2bd038f885d92f8c0021d482b23f9a38a003cd7bfc3e700e7e0afa971`,
GHCR manifest
`sha256:451c5e23a90e0df2fc904e8851aab12c3ec9ffdcd1258b6f14cf502222e46b5f`).
Both profiles serve checkpoint revision `629bc3218833`, the Hugging Face
branch `qad-step-4000`; its weights are byte-identical to the repository's
`main` branch, whose `config.json` differs only in architecture names. The
[machine-readable record](installer-tuning-20260925.json) holds the headline
values; [`installer-tuning-20260925/results`](installer-tuning-20260925/results)
holds every raw measurement.

## Conditions

Test containers are derived from each cluster's installer Compose files by
[`qwab.py`](decode-ab-20260925/qwab.py). A variant changes environment
settings, vLLM arguments or the image, or mounts changed Python files over the
image with its software receipts re-sealed
([`patch_overlay.py`](installer-tuning-20260925/programs/patch_overlay.py),
[`tree_overlay.py`](installer-tuning-20260925/programs/tree_overlay.py)).
Everything else stays as the installer deployment sets it.

Measurements, all with greedy requests:

- **Per-step decode time** (prose / code / JSON): after-first-token rate
  divided by tokens per step, from
  [`decode_probe.py`](installer-tuning-20260925/programs/decode_probe.py)
  inside [`measure.sh`](installer-tuning-20260925/programs/measure.sh), which
  also runs counting, arithmetic and code checks. Every configuration below
  passed those checks.
- **Steady-state step time at concurrency C**:
  [`concurrency_sweep.py`](installer-tuning-20260925/programs/concurrency_sweep.py)
  runs C identical requests at 256 and 768 output tokens and divides the
  difference in wall time by the difference in speculative steps, which
  cancels admission, prefill and ramp. Where stated, values are medians of
  three repeats.
- **Prefill**: tokens per second for one cold prompt with one output token,
  from [`prefill_curve.py`](installer-tuning-20260925/programs/prefill_curve.py)
  (best of two passes) or from `bench.py` inside `measure.sh`. With one output
  token the installer scheduler skips the MTP draft on the first chunk.
- **Token log-probability agreement**:
  [`logprob_probe.py`](installer-tuning-20260925/programs/logprob_probe.py)
  scores one fixed 1,151-token text with `prompt_logprobs`. Swapping one BF16
  GEMM kernel for another, with no precision change, moves the mean absolute
  difference by about 0.035 and rank-1 agreement to about 98%; that is the
  reference scale for the values below.

## Decode image

The image adds one layer to `dev-20260925-cuda1342-nccl2323-status031`,
generated by
[`qwen_decode_patch.py`](installer-tuning-20260925/programs/qwen_decode_patch.py)
and built by
[`build_qwen_decode.py`](installer-tuning-20260925/programs/build_qwen_decode.py):

- The Qwen4Exp low-latency GEMM hook runs beside B12X on GB10 with SM121
  skinny-GEMM plans for BF16 projections of up to 16 rows, measured by
  [`bench_skinny.py`](decode-ab-20260925/bench_skinny.py)
  ([sweep](decode-ab-20260925/gb10-skinny-gemm-sweep.json)).
- `VLLM_QWEN4_EXP_MXFP8_HC=1` quantizes the hyper-connection down/injection
  projections (97 in the target, 3 in the draft), which every rank reads in
  full at each step, to MXFP8 at load. Batches of at most 16 rows use the
  MXFP8 weights; larger batches use the retained BF16 weights, because the
  B12X MXFP8 kernel with BF16 activations runs 16-row tiles.

Per-step decode time on TP4, ms (prose / code / JSON):

| Configuration | Per step |
|---|---|
| Installer, image dev-20260925, MXFP8 LM head | 27.9 / 28.3 / 28.8 |
| SM121 plans | 27.2 / 27.8 / 27.6 |
| SM121 plans, MXFP8 hyper-connection for every batch | 26.1 / 26.6 / 26.4 |
| SM121 plans, MXFP8 hyper-connection up to 16 rows, 64-row all-reduce limit | 26.1 / 26.6 / 26.6 |
| Same, plus fused rotary embedding (below) | **25.5 / 25.9 / 26.1** |

On TP2 the installer measured 37.9 / 38.4 / 38.5 ms; with the image's
features, the 64-row all-reduce limit and fused rotary embedding it measured
35.7 / 36.3 / 36.3 ms, a steady-state C1 step of 36.0 ms.

Using MXFP8 for every batch lowered prefill: on TP2 from 4,214 / 3,921 to
4,063 / 3,753 tokens/s at 16K / 64K, on TP4 from 4,508 / 4,211 to
4,380 / 4,121. With BF16 above 16 rows, TP2 prefill measured
4,306 / 4,296 / 4,195 tokens/s at 8K / 16K / 32K.

The row limit was chosen from three repeats on TP2 (median steady step, ms):

| C | 1 | 4 | 5 | 8 | 16 |
|---|---|---|---|---|---|
| BF16 hyper-connection | 38.6 | 71.0 | 69.9 | 94.1 | 134.5 |
| MXFP8 up to 16 rows | **36.4** | **65.4** | 74.7 | 93.8 | 133.1 |
| MXFP8 up to 64 rows | 36.4 | 64.6 | 73.7 | 97.4 | 136.1 |

The C5 BF16 repeats spread from 66.5 to 76.7 ms.

## All-reduce routing

The Qwen collective policy sends an all-reduce to RoCEnante only up to
`QWEN_DISPATCH_AR_BYTES`; larger tensors go to NCCL. The feature default of
20,480 bytes admits four rows of the 2,560-wide BF16 activations, so from two
concurrent speculative requests (8 verification rows) every decode all-reduce
used NCCL; dispatch tracing (`QWEN_DISPATCH_TRACE=1`) confirmed it for every
captured row count from 5 to 64. Both profiles set 327,680 bytes, which covers
every CUDA-graph decode step (16 sequences × 4 rows).

Steady-state step time on TP4 (single run per point, ms):

| C | 1 | 2 | 3 | 4 | 5 | 6 | 8 | 10 | 12 | 14 | 16 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 20,480 bytes | 26.5 | 39.4 | 45.9 | 49.3 | 58.8 | 64.3 | 73.2 | 82.7 | 87.7 | 93.4 | 101.5 |
| 327,680 bytes | 26.1 | 35.1 | 39.8 | 45.4 | 50.9 | 56.7 | 64.3 | 74.3 | 79.4 | 81.2 | 94.5 |

On TP2, whole-run step time changed by between +0.5% and −10.3% across
C1–C16; the changes at C2 (+0.5%) and C4 (−1.3%) are inside run-to-run
spread. The smaller effect matches NCCL's lower cost on a direct link.

## Fused rotary embedding

QSA layers applied their M-RoPE through PyTorch operations, about 40 small
kernels per layer on the decode critical path. The profiles add
`"custom_ops":["+rotary_embedding"]` to `--compilation-config`, which runs the
fused rotary kernel instead.

| | Without | With |
|---|---|---|
| TP4 per step, ms | 26.1 / 26.6 / 26.6 | 25.5 / 25.9 / 26.1 |
| TP4 steady C1, median of 3, ms | 26.6 | 26.1 |
| TP2 steady C1, median of 3, ms | 36.4 | 36.0 |
| TP4 prefill 4K / 16K / 64K | 4,386 / 4,549 / 4,216 | 4,439 / 4,521 / 4,240 |

Log-probability agreement with and without the fused kernel on TP4: mean
0.035, 99th percentile 0.62, rank-1 98.6%.

## TP4 prefill: NCCL extended IPv4 GIDs

TP4 prefill spends about a third of GPU time in NCCL all-gather and
reduce-scatter for hyper-connection token-row ownership. Each Spark exposes
its two ring ports as four NIC functions across two PCIe domains. The image's
NCCL 2.32.3 publishes all four only with `NCCL_IB_EXTENDED_IPV4_GIDS=1`; with
it, the four ring channels use four RDMA devices (`NET/IB/0` to `3` in the
NCCL log). The Qwen TP4 profile sets it. Prefill with one output token,
tokens/s:

| Configuration | 4K | 8K | 16K | 32K | 64K |
|---|---|---|---|---|---|
| Image dev-20260924 (before paced RoCEnante), GIDs 0 | 4,434 | 4,728 | 4,756 | 4,494 | 4,246 |
| Decode image, NCCL 2.32.3, GIDs 0 | 4,402 | 4,672 | 4,659 | 4,485 | 4,224 |
| Decode image re-sealed with the base image's NCCL 2.31.2 | 4,927 | 5,219 | 5,179 | 4,986 | 4,706 |
| **Decode image, NCCL 2.32.3, GIDs 1** | **5,462** | **5,313** | **5,261** | **5,053** | **4,721** |

The NCCL 2.31.2 row uses the toolchain's `cuda` variant, built by
[`build_toolchain_variant.sh`](installer-tuning-20260925/programs/build_toolchain_variant.sh);
that build's routing reaches all four functions without the setting. Decode
per step with it was 27.1 / 27.5 / 27.4 ms, unchanged: decode all-reduces run
on RoCEnante. A source comparison of the vLLM, B12X and SparkRing trees of
this image and of the shared-2026.09.3 native image found no prefill-path
difference that favors the native image.

## Probabilistic drafting

The checkpoint's generation defaults sample at temperature 1.0, top-k 20 and
top-p 0.95, and apply to every request that does not set its own sampling.
With greedy drafting, the rejection test treats each draft token as certain,
so under sampling a draft token survives with the target's probability for it.
The profiles set `"draft_sample_method": "probabilistic"` in
`--speculative-config`: drafts sample from the draft distribution and the
rejection test uses the full probability ratio. Tokens per step from
`decode_probe.py` (three runs at temperature 1.0, two at temperature 0):

| Configuration | Prose | Code | JSON |
|---|---|---|---|
| TP2, greedy drafts, temperature 1.0 | 1.97 | 3.32 | 3.64 |
| TP2, probabilistic drafts, temperature 1.0 | **2.16** | 3.35 | 3.71 |
| TP2, probabilistic drafts, temperature 0 | 2.20 | 3.28 | 3.76 |
| TP4, greedy drafts, temperature 1.0 | 1.99 | 3.30 | 3.47 |
| TP4, probabilistic drafts, temperature 1.0 | **2.14** | 3.31 | 3.64 |
| TP4, probabilistic drafts, temperature 0 | 2.12 | 3.34 | 3.74 |

Step time and KV-cache capacity were unchanged (TP4 prose 25.8 and 25.7 ms;
3,131,214 tokens in both configurations), and temperature-0 acceptance stayed
within run-to-run spread of greedy drafting (2.18 / 3.30 / 3.71 on TP4).

## Measured and not adopted

**Local argmax for draft tokens** (`"use_local_argmax_reduction": true` in
`--speculative-config`): steady-state changes ranged from −12% to +8% across
C1–C16 without a pattern. The expected effect, 0.1 ms per step at C1 and about
0.9 ms at C5, is inside the run-to-run spread.

**Five decode patches**, each reviewed against the sources and switchable:
MTP feedback projections through the SM121 plan, multi-sequence MTP
draft-prefill compaction, draft-prefill CUDA graphs for every request count,
GDN metadata filled once per step, and a fused QSA q/k norm. Merged, they
raised TP2 prefill by 0.5–2.4% but slowed decode (median steady step, ms):

| TP2 | C1 | C8 |
|---|---|---|
| Configuration without the patches | 35.95 | 92.4 |
| All five patches | 37.2 | 94.8 |
| All but the MTP feedback route | 37.2 | 95.3 |
| All but the fused q/k norm | 37.2 | 93.3 |
| All but the GDN metadata change | 37.0 | 95.5 |
| All but multi-sequence compaction | 36.7 | 92.8 |
| All but every-request-count graphs | 36.8 | 93.7 |

No single switch restored the baseline, so the patches are not in the image.

## Limits

Each configuration ran on one TP2 pair or one TP4 ring. Identical requests
route every sequence to the same experts, so MoE cost at C > 1 is lower than
with mixed traffic. The test containers share the installer deployments'
settings but are not installer deployments. The TP2 profiles pin two NIC
functions and were not measured with extended GIDs; the GLM and MiMo TP4
profiles keep `NCCL_IB_EXTENDED_IPV4_GIDS=0` and were not measured with it.
